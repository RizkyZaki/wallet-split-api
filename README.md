# Wallet API

A small REST API for wallet operations and group expense splitting, built with
Node.js and Express. All data is held in memory, as required by the assignment.

## Quick start

Requires Node.js 18 or newer.

```bash
npm install
npm start
# Wallet API listening on http://localhost:3000
```

Run the test suite (Jest + Supertest, 38 tests):

```bash
npm test
```

No configuration is needed. Data lives only in memory and is wiped on every
restart. The port can be overridden with `PORT=4000 npm start`.

## Try it in 60 seconds

The snippet below walks through every feature. IDs are generated by the server,
so capture them from the responses (shown here with `jq`, but any tool works).

```bash
BASE=http://localhost:3000/api

# 1. Create two wallets
ALICE=$(curl -s -X POST $BASE/users -H 'Content-Type: application/json' \
  -d '{"name":"Alice","initialBalance":100}' | jq -r .id)
BOB=$(curl -s -X POST $BASE/users -H 'Content-Type: application/json' \
  -d '{"name":"Bob"}' | jq -r .id)

# 2. Top up Bob
curl -s -X POST $BASE/users/$BOB/topup -H 'Content-Type: application/json' \
  -d '{"amount":20}'

# 3. Transfer from Alice to Bob
curl -s -X POST $BASE/transfers -H 'Content-Type: application/json' \
  -d "{\"fromUserId\":\"$ALICE\",\"toUserId\":\"$BOB\",\"amount\":25}"

# 4. Alice pays a 10.00 dinner, split equally between the two of them
curl -s -X POST $BASE/expenses -H 'Content-Type: application/json' \
  -d "{\"payerId\":\"$ALICE\",\"participantIds\":[\"$ALICE\",\"$BOB\"],\"totalAmount\":10}"

# 5. Check balances and history
curl -s $BASE/users/$ALICE/balance
curl -s $BASE/users/$BOB/transactions
```

## API reference

All requests and responses are JSON. Monetary amounts are plain numbers with
at most two decimal places (e.g. `10.5`).

### Create a wallet

`POST /api/users`
```json
{ "name": "Alice", "initialBalance": 100 }
```
`initialBalance` is optional and defaults to `0`. Responds `201`:
```json
{ "id": "user_...", "name": "Alice", "balance": 100 }
```

### Top up a wallet

`POST /api/users/:id/topup`
```json
{ "amount": 50 }
```
Responds `200` with the transaction record, including `balanceAfter`.

### Transfer between users

`POST /api/transfers`
```json
{ "fromUserId": "user_...", "toUserId": "user_...", "amount": 25 }
```
Responds `200` with both users' new balances.

### Create a group expense

`POST /api/expenses`
```json
{
  "payerId": "user_...",
  "participantIds": ["user_...", "user_..."],
  "totalAmount": 100,
  "splitType": "equal"
}
```
`splitType` defaults to `"equal"`. For a custom split, set it to `"custom"`
and provide `splits`, one entry per participant, whose amounts must add up to
`totalAmount` exactly:
```json
{
  "payerId": "user_...",
  "participantIds": ["user_...", "user_..."],
  "totalAmount": 100,
  "splitType": "custom",
  "splits": [
    { "userId": "user_...", "amount": 60 },
    { "userId": "user_...", "amount": 40 }
  ]
}
```
Responds `201` with the stored expense, including the resolved `splits`.

### Read endpoints

- `GET /api/users/:id/balance`
- `GET /api/users/:id/transactions` – chronological list of this user's entries
- `GET /api/expenses/:id`
- `GET /health`

### Errors

Every error has the shape `{ "error": "message" }` with an appropriate HTTP
status: `400` for validation failures (including malformed JSON), `404` for
unknown users or expenses, `500` only for unexpected internal errors.

## Validation rules

- Every amount (top-up, transfer, expense total, custom split entry) must be a
  positive number with at most two decimal places.
- The sender (transfers) or payer (expenses) must have sufficient balance.
  Validation completes before any balance is modified, so a rejected request
  never leaves partial changes behind.
- Every referenced user ID must exist, otherwise the response is `404`.
- `participantIds` must be non-empty and must not contain duplicates.
- A custom split must list every participant exactly once, and the amounts
  must sum to the expense total.
- A user cannot transfer to themselves.

## Design decisions

**Money is handled in integer cents.** Amounts enter and leave the API as
decimals, but every addition, subtraction, comparison and sum in
`src/utils/money.js` converts to cents first. Naive float arithmetic drifts
(`0.1 + 0.2 === 0.30000000000000004`), which is unacceptable for balances.
Amounts with more than two decimal places are rejected rather than silently
rounded, and there is an upper bound so the cents value always stays an exact
integer.

**How a group expense moves money.** The payer is treated as having fronted
the whole bill (like paying at a restaurant), so `totalAmount` is debited from
the payer's wallet immediately. Each participant's share is recorded in their
transaction history as an `EXPENSE_SHARE` entry ("owes Alice for shared
expense") but is **not** debited from their wallet automatically.

This keeps "recording an expense" and "settling a debt" as separate steps:
settlement is an ordinary `POST /api/transfers` to the payer. I chose this
because the specification only requires checking the *payer's* balance, not
each participant's, and auto-debiting participants with an empty wallet would
have to fail in ways the spec does not describe. The payer does not have to be
in `participantIds` (they may be paying purely on behalf of others); include
their ID when they are part of the split.

**Equal split remainders.** 10.00 split three ways cannot be exact in
currency. Shares are computed in cents; any leftover cents are given one each
to the earliest participants in the list (`[3.34, 3.33, 3.33]`). This
guarantees the shares always sum to `totalAmount` exactly.

**In-memory storage.** Three `Map`s in `src/store.js` (users, transactions,
expenses). Only the service layer touches them, so swapping in a real database
would mean changing the store and services, not the HTTP layer.

**Transaction log as the source of history.** Every balance-changing operation
(initial balance, top-up, both legs of a transfer, expense payment) appends an
immutable record with `balanceAfter`. `GET /api/users/:id/transactions` simply
filters that log; because the `Map` preserves insertion order, the result is
already chronological.

**Atomicity and concurrency.** Every handler is synchronous and Node.js runs
JavaScript on a single thread, so a request cannot be interleaved with another
between "check balance" and "deduct balance". Combined with validate-then-
mutate ordering, each request is effectively atomic. Moving to a real database
would require an explicit transaction with row locking (or optimistic
versioning) to keep that guarantee.

**Error handling.** A single `AppError` class carries the HTTP status and is
caught by one Express error middleware. Validation errors from all services
therefore share the same `{ "error": "..." }` shape without `try/catch` in
every route. Unexpected exceptions are logged and returned as a generic `500`
so internal details never leak.

## Project structure

```
src/
  app.js                        # Express setup (routes + middleware)
  server.js                     # entry point
  store.js                      # in-memory Maps + ID generation
  utils/money.js                # cents-based arithmetic and amount validation
  errors/AppError.js
  services/
    userService.js              # create, top-up, balance, history
    walletService.js            # transfers
    expenseService.js           # group expenses, equal/custom split
    transactionService.js       # append-only transaction log
  controllers/                  # thin HTTP adapters over the services
  routes/
  middleware/errorHandler.js
tests/
  api.test.js                   # end-to-end tests via Supertest, one per validation rule
  money.test.js                 # unit tests for the money helpers
  splitEqually.test.js          # unit tests for remainder distribution
```
